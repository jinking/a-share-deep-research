# 证据对象规范（Evidence Layer，v3.0）

> 适用版本：`manifest_version = 3`
> 关联代码：`core/models/`、`core/evidence/`、`core/validation/`
> 关联命令：`scripts/build_evidence.py`、`scripts/validate_evidence.py`、`scripts/validate_report.py --evidence-dir`

## 1. 为什么要有这一层

v2 的 `research_manifest.evidence[]` 只能记录「这条结论声称来自哪份文件、第几页」。
Validator 只能判断字段**填得像不像真的**，无法确认：

- 这份文档是否真实存在；
- 第 12 页是否存在、是否真的写了这句话；
- 所谓「两个独立来源」是否其实都转引自同一篇上游报道。

v3.0 把证据从「一段文字描述」升级为**可机器校验的对象**，形成一条可反向追踪的链条：

```text
Research Conclusion → Claim → EvidenceLink → SourceDocument → page/section/paragraph/table → 原文
```

## 2. 三层对象模型

| 对象 | 回答的问题 | 关键字段 |
|---|---|---|
| `SourceDocument` | 信息**从哪来** | `document_id`、`source_type`、`source_group`、`sha256`、`url`/`local_path` |
| `Claim` | 研究了**什么结论** | `claim_id`、`category`、`level`、`materiality`、`status`、`basis_claim_ids` |
| `EvidenceLink` | 证据**怎么支撑**结论 | `page/section/paragraph/table`、`evidence_text`、`support_type`、`confidence` |
| `EvidenceCandidate` | 有谁**看见过**这条线索 | `candidate_id`、`source_type`、`url`、`upstream_hint`、`status` |

> `EvidenceCandidate` 不属于证据 —— 它只是「线索」。正式验收只认前三个对象，详见 §6。

落盘位置（每个研究目录一份）：

```text
research_sz002897/
└── evidence/
    ├── candidates.jsonl      # 一行一个 EvidenceCandidate（线索，不参与证据校验）
    ├── documents.jsonl        # 一行一个 SourceDocument
    ├── claims.jsonl           # 一行一个 Claim
    ├── evidence_links.jsonl   # 一行一个 EvidenceLink
    └── raw/                   # 原始证据文件（PDF / HTML / 截图）
```

逐行 JSON（JSONL），UTF-8，空行忽略。Schema 见 `schemas/*.json`。

## 3. ID 规范

| 对象 | 格式 | 说明 |
|---|---|---|
| Document | `DOC_<指纹前8位>` | 指纹优先取 `url`；无 url 时取 `issuer + published_at + title`。**禁止用递增序号** |
| Claim | `C_<领域>_<主题>_<期间>` | 语义稳定 ID，如 `C_FIN_REV_2026H1`、`C_ORDER_224G_STATUS`；**不要用 C001**，否则 v3.2 增量重算无法复用 |
| Evidence | `EV_<claim_id>_<两位序号>` | 由 `EvidenceStore.next_evidence_id()` 生成 |
| Candidate | `CAN_<指纹前8位>` | 指纹优先取 `url`；无 url 时取 `provider + discovered_at + title`。前缀 `CAN_` 是硬约定：校验器靠它拦截「把线索当证据」 |

## 4. 等级（level）与重要度（materiality）

```text
事实类      fact
表述类      management_statement      （公司/管理层口径 ≠ 已兑现）
推理类      inference / assumption
未决类      unconfirmed / third_party_consensus
确认级      confirmed_revenue / confirmed_order / design_win / mass_production / batch_delivery
```

- **确认级**（`PRIMARY_REQUIRED_LEVELS`）必须至少有一个**一手来源** Document：
  `annual_report` / `interim_report` / `quarterly_report` / `company_announcement` /
  `exchange_filing` / `company_ir` / `customer_announcement` / `government` / `official_database`。
  **券商研报、媒体、自媒体不可升级为确认级。**
- **已确认收入 / 已确认订单 / 已量产 / 已批量交付** 还必须存在至少一条 `support_type = direct` 且来自一手来源的链接。

`materiality` 决定校验强度：

| materiality | 强制要求 |
|---|---|
| `critical` | 必须有证据绑定、必须有定位、必须有 `evidence_text` 摘录 |
| `major` | 必须有证据绑定 |
| `normal` | 只做引用完整性检查 |

> 按规范，只有 `critical` / `major` 进入严格 Evidence Validation。不要为了「形式完整」把整篇报告的文字都变成 Claim——只对**影响预测、估值、风险等级、研究状态、证伪条件**的结论强制 Claim 化。

## 5. 定位（locator）与来源独立性

- 定位：`page` / `section` / `paragraph` / `table` **至少命中一种**；`page` 不得越界（文档登记了 `page_count` 时）。
- `evidence_text` 必须是**原文摘录**：不得改写、不得脑补、不得写自己的总结。
- 独立性：同一上游的转载共享同一个 `source_group`（例如财联社原始报道、新浪转载、雪球转载 → 同一个 `source_group`），**只算一个独立来源**。
  需要双源确认的 Claim 置 `requires_two_sources = true`。

## 6. 线索（EvidenceCandidate）：线索 ≠ 证据

研究过程中最先出现的东西**不是**证据，而是线索：搜索结果、neodata 摘要、券商转述、
媒体报道、交流群里的一张截图。它们共同的特征是：**能指向一个出处，但还不能被复核**。

如果把它们直接写进 `documents.jsonl`，证据链就烂了 —— 因为「可点击」和「可复核」
是两件事。所以单独开一层：

| 字段 | 含义 |
|---|---|
| `candidate_id` | `CAN_<hash8>`，必须以此前缀开头 |
| `source_type` | 复用 Document 的来源类型枚举 |
| `title` / `url` / `snippet` | 线索本身的信息 |
| `discovered_at` | 发现时间（不是发布时间 —— 线索常常不知道发布时间） |
| `provider` | 发现渠道，如 `neodata` / `westock` / `search` |
| `upstream_hint` | 上游出处提示，用于判断两条线索是否同源 |
| `status` | `new` / `reviewed` / `promoted` / `rejected` / `duplicate` |
| `promoted_document_id` | 升级成功后回填的正式 Document |

**线索永远不能**：

- 满足 `EVIDENCE_PRIMARY_REQUIRED`（它不是一手来源）；
- 满足 `EVIDENCE_DIRECT_REQUIRED`（没有直接支持关系）；
- 提供 critical Claim 的 locator 或 `evidence_text`；
- 参与正式来源独立性计数。

`status=promoted` **本身也不构成证据** —— 它只表示「这条线索已经拿到原件并落盘」。
真正的证据仍然只认 `SourceDocument` + `EvidenceLink`。因此：

- 线索被当成 Claim / Document 引用 → P0 `CANDIDATE_USED_AS_EVIDENCE`；
- 线索标成 `promoted` 却没有对应 Document → P1 `CANDIDATE_PROMOTED_WITHOUT_DOCUMENT`。

从线索到证据只有一条通道，见 §9 的 `promote_evidence_candidate.py`。

## 7. 时间模型（v3.0.1）

历史上只有一个 `research_date`，它同时被当成四种含义：数据截止日、研究基准日、
行情截止日、报告生成日。语义模糊到无法回答一个基本问题：**这条证据是否超出了研究时点**。

v3.0.1 把它拆成三个明确时点（写在 `manifest.meta`）：

| 字段 | 含义 | 约束 |
|---|---|---|
| `as_of` | 研究信息截止时点 | Evidence 的 `published_at <= as_of` |
| `market_data_as_of` | 行情数据截止时点 | 用于当前价 / 市值 / 技术面 / K 线；不得晚于 `generated_at` |
| `generated_at` | 报告生成时间 | 必须与报告内时间戳（title / h1 / footer / 顶部注释）及文件名一致 |

- 三者都可缺省；但**一个都没有**属于结构错误（`MANIFEST_V3_STRUCTURE`）。
- 仍只有 `research_date` → P2 `TIME_MODEL_LEGACY`，不阻断，但会提示迁移。
- 新模型下证据超时点报 `SOURCE_DATE_AFTER_AS_OF`；旧模型保留
  `SOURCE_DATE_AFTER_RESEARCH_DATE`，v2 行为零变化。

## 8. 校验规则与错误码

错误码格式固定为「领域_问题」，稳定、可搜索、不可随意改名（详见 `core/validation/codes.py`）。

| 级别 | 错误码 | 触发条件 |
|---|---|---|
| P0 | `EVIDENCE_DOC_MISSING` | Claim 指向不存在的 Document |
| P0 | `EVIDENCE_HASH_MISMATCH` | 本地文件 hash 与登记值不同（证据被替换） |
| P0 | `EVIDENCE_PRIMARY_REQUIRED` | 确认级 Claim 缺少一手来源 |
| P0 | `EVIDENCE_DIRECT_REQUIRED` | 确认级 Claim 无 `direct` 证据，或 direct 证据不来自一手来源 |
| P0 | `CANDIDATE_USED_AS_EVIDENCE` | 把线索（Candidate）当成正式证据引用 —— 线索 ≠ 证据 |
| P1 | `EVIDENCE_LOCATOR_MISSING` | critical Claim 无任何定位 |
| P1 | `EVIDENCE_LOCATOR_INVALID` | 定位越界或指向文档未登记的章节 |
| P1 | `EVIDENCE_TEXT_MISSING` | critical Claim 缺少原文摘录 |
| P1 | `EVIDENCE_SOURCE_NOT_INDEPENDENT` | 所谓「双源」实为同一上游转载 |
| P1 | `EVIDENCE_NO_SOURCE` | Document 既无 url 也无 local_path |
| P1 | `EVIDENCE_CLAIM_MISSING` | Evidence 指向不存在的 Claim |
| P1 | `EVIDENCE_CLAIM_ORPHAN` | critical/major Claim 完全没有证据绑定 |
| P1 | `EVIDENCE_SUPPORT_BROKEN` | `status=supported` 但支持证据全部失效 |
| P1 | `EVIDENCE_DUPLICATE_ID` | `document_id` / `claim_id` / `evidence_id` 重复 |
| P1 | `EVIDENCE_MODEL_INVALID` | 模型字段非法（`source_type`、`level`、`page` 等） |
| P1 | `EVIDENCE_PARSE` | JSONL 行无法解析 |
| P1 | `EVIDENCE_REF_UNKNOWN` | `manifest.evidence_refs` 指向不存在的 Claim |
| P1 | `EVIDENCE_REFS_EMPTY` | v3 manifest 未声明任何关键 Claim |
| P1 | `SOURCE_DATE_AFTER_RESEARCH_DATE` | **旧时间模型**：证据发布时间晚于 `research_date` |
| P1 | `SOURCE_DATE_AFTER_AS_OF` | **新时间模型**：证据发布时间晚于 `as_of` |
| P1 | `MARKET_DATA_AFTER_GENERATED_AT` | 行情数据时点晚于报告生成时点 |
| P1 | `GENERATED_AT_MISMATCH` | `generated_at` 与报告内时间戳/文件名不一致 |
| P1 | `CLAIM_BASIS_UNKNOWN` | `basis_claim_ids` 指向不存在的 Claim |
| P1 | `CLAIM_BASIS_LEVEL_INVALID` | `fact` 级 Claim 依赖 `inference` / `assumption` / `unconfirmed` |
| P1 | `CLAIM_UNCONFIRMED_SUPPORTED` | 未确认等级（`assumption` / `unconfirmed`）却被标成 critical/major `supported` |
| P1 | `CANDIDATE_PROMOTED_WITHOUT_DOCUMENT` | 线索标为 `promoted` 却没有对应正式 Document |
| P1 | `EVIDENCE_STORE_MISSING` | v3 产物未提供 Evidence Store |
| P1 | `MANIFEST_VERSION_UNSUPPORTED` | `manifest_version` 不在支持范围 |
| P1 | `MANIFEST_V3_STRUCTURE` | v3 manifest 缺必需区块，或时间字段一个都没给 / 无法解析 |
| P1 | `MANIFEST_EVIDENCE_REFS_FORMAT` | `evidence_refs` 结构非法（非对象 / 缺 `claim_id`） |
| P2 | `EVIDENCE_HASH_UNVERIFIED` | 无本地副本或无 hash，无法校验原始版本 |
| P2 | `EVIDENCE_IMPORTANCE_MISMATCH` | manifest `importance` 与 Claim `materiality` 不一致 |
| P2 | `EVIDENCE_STORE_SKIPPED` | v2 兼容模式：只做引用完整性 |
| P2 | `TIME_MODEL_LEGACY` | 仍只有 `research_date`，未采用 `as_of` / `market_data_as_of` / `generated_at` |

`P0` / `P1` 任一出现即**禁止标记研究完成**。

## 9. 工作流

```bash
# 1) 初始化证据库
python3 scripts/build_evidence.py init research_sz002897/evidence

# 2) 登记原始文档（自动复制进 raw/ 并计算 sha256；document_id 自动生成）
python3 scripts/build_evidence.py register research_sz002897/evidence \
  --file ~/Downloads/2026H1.pdf \
  --type interim_report \
  --title "意华股份2026年半年度报告" \
  --issuer 意华股份 \
  --published-at 2026-08-25 \
  --url "https://www.cninfo.com.cn/..." \
  --group CNINFO_002897_2026H1 \
  --pages 168

# 3) 查看清单 / 复核原始文件是否被替换 / 只校验证据库
python3 scripts/build_evidence.py show     research_sz002897/evidence
python3 scripts/build_evidence.py verify   research_sz002897/evidence
python3 scripts/validate_evidence.py       research_sz002897/evidence

# 4) 正式验收（报告 + v3 manifest + 证据库）
python3 scripts/validate_report.py <report.html> \
  --manifest research_sz002897/research_manifest.v3.json \
  --evidence-dir research_sz002897/evidence \
  --out research_sz002897/validation
```

### 线索 → 证据（唯一通道）

搜索阶段先记线索，等拿到原件再 promote。**不要跳过 promote 直接手写 Document**：

```bash
# a) 登记线索（线索 ≠ 证据）
python3 scripts/build_evidence.py add-candidate research_sz002897/evidence \
  --type media --title "财联社：意华股份高速连接器进展" \
  --url "https://www.cls.cn/detail/123" --claim C_ORDER_224G_STATUS \
  --provider neodata --upstream CLS_20260915_001

# b) 列线索（不参与证据校验）
python3 scripts/build_evidence.py candidates research_sz002897/evidence

# c) 确认原件已在手 → promote（演练 + 正式）
python3 scripts/promote_evidence_candidate.py research_sz002897/evidence \
  --plan promote_plan.json --dry-run
python3 scripts/promote_evidence_candidate.py research_sz002897/evidence \
  --plan promote_plan.json
```

`promote_plan.json` 里 `links[].evidence_text` 可以手写，也可以只给
`excerpt_anchor`（+ `excerpt_tail`）让脚本**从原文剪**出片段 —— 后者更不容易出错：

```json
{
  "promotions": [
    {
      "candidate_id": "CAN_3f9a1b2c",
      "document": {
        "source_type": "interim_report",
        "title": "意华股份2026年半年度报告",
        "url": "https://www.cninfo.com.cn/...",
        "local_file": "raw/2026H1.txt",
        "source_group": "CNINFO_002897_2026H1"
      },
      "links": [
        {
          "claim_id": "C_FIN_REV_2026H1",
          "section": "主要会计数据",
          "excerpt_anchor": "营业收入 2,863,320,150.75 元",
          "excerpt_tail": 11
        }
      ]
    }
  ]
}
```

promote 的五条硬规则（已代码化，不靠自觉）：

1. 无 `url` 且无 `local_file` → **拒绝**。线索不能凭「我记得看过」变成证据；
2. 文本原件的 `evidence_text` 必须是文件真实子串（忽略空白差异）。
   **PDF 等二进制第一版不做 OCR，跳过子串校验**——这是硬闸的已知边界，不能装作不存在：
   请把原件的**官方文本层**一起留存并单独比对（`examples/意华股份002897_样板/` 即如此），
   并在摘录的 `note` 里如实写明复核方式；critical Claim 缺摘录仍报 P1 `EVIDENCE_TEXT_MISSING`；
3. **两阶段原子执行** —— 任一条不通过则整体不落盘，落盘阶段异常回滚内存状态；
4. **幂等** —— 重复 promote 到同一份 Document 视为无变化并放行；指向另一份 Document 则明确拒绝（不许悄悄改指向）；
5. **永不写 `claims.jsonl`** —— Claim 能否 `supported` 只由 Document + EvidenceLink 决定，不由线索决定；
   计划文件里出现 `claim_status` / `claim_status_updates` 直接拒绝。

> 硬规则 2 的边界提示：`text_supports_excerpt()` 对非文本后缀返回「跳过校验」，
> 所以**不能**拿它给 PDF 摘录背书。要么留文本层比对，要么在 `note` 里承认未经机器复核。

Claims / EvidenceLinks 由研究流程写入 `claims.jsonl` 与 `evidence_links.jsonl`
（可用 `EvidenceStore.add_claim()` / `add_link()`，或直接编辑 JSONL 后由 `validate_evidence.py` 校验）。

## 10. v2 → v3 迁移

```bash
python3 scripts/migrate_manifest_v2_to_v3.py research_manifest.json \
  --out research_manifest.v3.json \
  --evidence-dir research_sz002897/evidence \
  --critical E001,E002,E007
```

迁移纪律：

- 只做结构化搬运；**不自动宣称证据已验证**，所有迁移对象带 `migration_status = "needs_verification"`；
- 迁移出的 critical Claim **必然**报 `EVIDENCE_LOCATOR_MISSING` / `EVIDENCE_TEXT_MISSING`，必须人工补齐定位与原文摘录后才可能通过；
- `level` 由中文映射为 v3 等级（`事实→fact`、`管理层口径→management_statement`、`已确认订单→confirmed_order` …）；无法识别时降级为 `unconfirmed` 并在 `note` 中留下原因；
- 同一份财报的不同视角（「半年报·分行业情况」「半年报·现金流量表」）会收敛为**同一个 Document**，避免人为放大来源数量。

## 11. 不允许的实现方式

1. **不允许把证据校验写成 Prompt**。校验必须由程序读 Document、算 hash、查定位完成，不得让 Agent「自己判断 source_ref 是否真实」。
2. **不允许 Validator 修改产物**。Validator 只能输出 `PASS/FAIL + 错误码 + 位置 + 建议修复项`，不得自动补 Claim、自动改证据等级、自动修正预测或写回 Manifest。
3. **不允许为「形式完整」给所有文字建 Claim**。
4. **不允许通过改测试期望让测试变绿**，除非需求本身已明确变更。
