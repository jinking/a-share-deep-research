# A股个股深度研究 · 产物验收规则

## 目的

研究生成器负责“做研究”，Validator 负责“验研究”。两者职责分离，避免同一个 Agent 对自己的产物自我放行。

正式研究只有在 `scripts/validate_report.py` 返回 **PASS** 后，才能标记为“研究完成”。

## 交付物

每次完整研究至少生成四类文件：

1. `report.html` 或 `report.md` —— 人读报告
2. `research_manifest.json` —— 机器可审计的关键模型与证据清单
3. `validation/validation_report.json` —— 机器验收结果
4. `validation/validation_report.md` —— 人读验收结果

`research_manifest.json` 使用 `assets/research_manifest.template.json` 作为骨架。

## 阻断等级

- **P0 硬错误**：直接 FAIL，不允许交付。
  - 0–16章缺章
  - 悲观/中性/乐观 × 连续3年不完整
  - EPS×股本 ≠ 归母净利润
  - 现价×股本 ≠ 市值
  - 盈利预测、估值、SOTP 使用的同年中性利润口径冲突
  - SOTP 分部利润/估值之和与总值不一致
  - “已确认订单/已量产/已批量交付”等确认级结论只来自券商、自媒体、传闻等低等级来源
  - Claim 指向不存在的 Document（`EVIDENCE_DOC_MISSING`）
  - 本地原件哈希与登记值不符，即证据被事后替换（`EVIDENCE_HASH_MISMATCH`）
  - 确认级 Claim 缺少允许的一手来源，或只有 `context` 级支持（`EVIDENCE_PRIMARY_REQUIRED` / `EVIDENCE_DIRECT_REQUIRED`）
  - 把线索（`EvidenceCandidate`）当成正式证据引用（`CANDIDATE_USED_AS_EVIDENCE`）
  - **跨产物冲突（v3.0.2）**：报告引用了不存在的 Claim（`REPORT_CLAIM_UNKNOWN`）、把 `status=pending` 的 Claim
    当成确定性结论（`REPORT_PENDING_CLAIM_ASSERTED`）、把未确认等级写成 `fact` / `confirmed_*`
    （`REPORT_UNCONFIRMED_AS_FACT`）、报告声明的 `level` 与 Ledger 不一致（`REPORT_CLAIM_LEVEL_MISMATCH`）
  - **Claim 版本漂移（v3.0.3）**：报告锚点声明的 `data-claim-fingerprint` 与当前 Claim 不符，
    或者索性没声明指纹（`REPORT_CLAIM_REVISION_MISMATCH`）。
    `claim_id` / `level` / `status` 三个属性都对，也可能复述的是**上一版**结论 —— 这是最隐蔽的一条缝。
  - **假「已验证」摘录（v3.0.3）**：链接写着 `excerpt_verification_status=verified`，
    机器重算却对不上原文（原文在、可比对、不命中）→ `EVIDENCE_EXCERPT_VERIFICATION_MISMATCH`。
    注意与 P2 `EVIDENCE_HASH_UNVERIFIED` 的区别：那是「原件不在、无法比对」，这是「证据被替换」。
- **P1 重要缺陷**：严格模式下 FAIL。
  - 证据清单缺失关键字段
  - 季度跟踪指标不足10项或超过15项
  - 最终状态不在允许状态集合
  - 关键证伪条件不足
  - critical Claim 无任何定位 / 缺少原文摘录（`EVIDENCE_LOCATOR_MISSING` / `EVIDENCE_TEXT_MISSING`）
  - 所谓“双源”实为同一上游转载（`EVIDENCE_SOURCE_NOT_INDEPENDENT`）
  - critical Claim 的摘录未经验证（`EVIDENCE_EXCERPT_UNVERIFIED`，v3.0.2）
  - 正式 v3 时间模型不完整（`TIME_MODEL_INCOMPLETE`，v3.0.2）
  - 报告声明的 `status` 与 Ledger 不一致（`REPORT_CLAIM_STATUS_MISMATCH`）
  - `importance=critical` 的 Claim 在报告中没有任何落点（`REPORT_CRITICAL_CLAIM_MISSING`）
  - **上游引用无法核实（v3.0.3）**：`upstream_document_id` 指向本库不存在的 Document，
    或上游链成环（`EVIDENCE_UPSTREAM_UNKNOWN`）。外部系统编号请写 `upstream_external_id`。
  - **strict Claim 从 manifest 消失（v3.0.3）**：`scope=report` 的 critical / major Claim
    不在 `manifest.evidence_refs` 里（`MANIFEST_STRICT_CLAIM_MISSING`）。
    内部中间结论请显式标 `scope=internal`，不要靠删 manifest 隐藏。
  - **服务商冒充一手来源（v3.0.3）**：`provider` 是数据服务商的 Document 写了
    一手 `source_type`（`EVIDENCE_MODEL_INVALID`）。
- **P2 改进项**：允许交付，但下一版应修。
  - 无本地副本或无哈希，无法校验原始版本（`EVIDENCE_HASH_UNVERIFIED`）
  - 仍只有 `research_date`，未采用新时间模型（`TIME_MODEL_LEGACY`）
  - v2 兼容模式：只做引用完整性，不执行证据真实性校验（`EVIDENCE_STORE_SKIPPED`）

完整错误码表（含触发条件）见 `references/证据对象规范.md` §8 与 `core/validation/codes.py`；
错误码格式固定为「领域_问题」，**稳定、可搜索、不可随意改名**。

## 三情景三年硬规则

正式报告必须完整输出：

| | Y+1 | Y+2 | Y+3 |
|---|---:|---:|---:|
| 悲观 | 必填 | 必填 | 必填 |
| 中性 | 必填 | 必填 | 必填 |
| 乐观 | 必填 | 必填 | 必填 |

不能出现“2026 三情景 + 2027/2028 只有中性”的缩水版本。

## 模型对账硬规则

同一个目标年度的“中性归母净利润”只能有一个权威值：

**盈利预测 → 估值 → SOTP → 隐含预期反推**

如果 SOTP 把业务拆开，所有纳入利润对账的分部利润之和必须回到同年的公司中性归母；尚未盈利的期权业务可只给期权市值，但必须设置 `include_in_profit_reconciliation=false`，防止利润重复计算。

## 证据升级硬规则

以下确认级标签：

- 已确认收入
- 已确认订单
- 已定点
- 已量产
- 已批量交付 / 批量供货

必须至少有以下一类一手来源：公司公告/财报、交易所文件、公司投资者关系记录、客户官方公告、政府/官方数据库。

券商研报、机构纪要转述、媒体、自媒体、股吧只能作为线索或第三方口径，不能自动升级成“已确认”。

### Provider ≠ Source，且 Provider 永远不是 Primary（v3.0.2 → v3.0.3 收严）

`westock-data` / `westock` / `neodata` 这类取数服务是**数据服务商（Provider）**，不是**来源（Source）**。
它们把交易所公告、行情、股东名册搬运过来，但**搬运不产生一手性**。

- `source_type` 只能是 `data_vendor` / `third_party_database`，**不得**自称 `official_database`；
- **声明上游也不再授予一手资格**（v3.0.2 的那条通行证已废除）。一手性属于上游那份原件本身，
  上游关系只用来**合并来源独立性**；
- 上游关系有两种写法，不要混用：
  - `upstream_document_id` —— **本库** Document 的 ID，必须真实存在（否则 P1 `EVIDENCE_UPSTREAM_UNKNOWN`）；
  - `upstream_external_id` —— **外部系统**的编号（如巨潮编号），不做存在性校验。
- 来源独立性按 `independence_key` 归并：沿 `upstream_document_id` 多级传递，
  上游不在库时用 `upstream_external_id`；**成环时整环只算一个来源**
  （否则两条互相转载的稿件就能满足「双源确认」）。
- 因此「westock-data + 公司公告」是**一个**来源，不是两个。

这条规则由代码强制（`core/models/provenance.py` + `SourceDocument.validate`），不靠自觉。

### 摘录必须是可复核的原文，且状态由机器算（v3.0.2 → v3.0.3 收严）

- `evidence_text` 必须是原件里的**真实摘录**，不得改写、不得总结、不得脑补；
- 每条链接必须显式声明 `excerpt_verification_status`：`verified` / `unverified` / `not_applicable`；
- **`verified` 必须说明验证手段**（`direct_text` / `text_layer` / `manual` / `ocr`）；
- **「跳过了校验」不等于「已验证」**：PDF 无文本层、只有 URL、原件缺失 → `unverified`；
  未声明状态同样按未验证处理。critical Claim 的摘录未经验证 = P1 `EVIDENCE_EXCERPT_UNVERIFIED`。
- 状态只能由机器比对写入（`scripts/verify_excerpts.py` / `stamp_excerpt_verification`），**不允许手工填 `verified`**；
- **落盘状态只是缓存**（v3.0.3）：校验器会重新算一遍并与它比对，
  `stored=verified` 而重算不通过 = P0 `EVIDENCE_EXCERPT_VERIFICATION_MISMATCH`；
  promote 计划里出现 `excerpt_verification_*` 三字段会被直接拒绝。
- 拿不到原文（无本地文件 / 无文本层）时**不报 mismatch** —— 那是「无法比对」，
  由 P2 `EVIDENCE_HASH_UNVERIFIED` 负责，不是「摘录是假的」。

### 报告锚点必须绑定 Claim 版本（v3.0.3）

影响预测 / 估值 / 风险 / 最终状态 / 证伪条件的结论，锚点除
`data-claim-id` / `data-claim-level` / `data-claim-status` 外，**还必须给 `data-claim-fingerprint`**
（Markdown 写 `fingerprint=`）。指纹由 `core/models/fingerprint.py` 现算：

```text
sha256(canonical_json({claim_id, normalize_claim_text(claim), level, status}))[:16]
```

- 指纹不符 → P0 `REPORT_CLAIM_REVISION_MISMATCH`；
- **没给指纹同样报这个码** —— 没有版本可比就不能放行，否则「删掉属性」会成为绕过路径；
- 报告允许对结论做人类可读改写，本规则**不**比较报告可见文本与 Claim 正文；
- 盖章用 `scripts/stamp_claim_fingerprints.py`（`--check` 只校验、`--write` 才落盘），
  **不要手填**。

### 时间模型必须完整，且 Schema 与 Runtime 同一口径（v3.0.2 → v3.0.3 对齐）

正式 v3 manifest 一旦声明 `as_of`，就必须同时给出 `market_data_as_of` 与 `generated_at`——
只写一部分会让时效校验悄悄退化。缺字段 = P1 `TIME_MODEL_INCOMPLETE`。
只保留 `research_date` 的旧 v3 走兼容路径（P2 `TIME_MODEL_LEGACY`），**不要声明 `as_of`**。

`schemas/research_manifest.v3.schema.json` 用同一套 `if/then/else` 表达这条规则，
因此「Schema 通过、Runtime 却报结构错误」这种两边说法不一致的情况不再可能。

`published_at` 推荐写到 `YYYY-MM-DDTHH:MM:SS+08:00` 精度；只写到「日」时退化为 day-level 比较，
**禁止**拿 `00:00` 冒充一个真实时刻。

### strict Claim 必须反向进 manifest（v3.0.3）

`Claim` 的 `scope` 默认 `report`。`scope=report` 的 critical / major Claim **必须**出现在
`manifest.evidence_refs` 中，否则 P1 `MANIFEST_STRICT_CLAIM_MISSING`。

反向链三层不可绕过：

```text
Claim Ledger  →  manifest.evidence_refs  →  Report Claim Anchor
```

确有内部中间结论时，把 Claim 标成 `scope=internal` —— 让「为什么它不在清单里」
是一条可审查的记录，而不是一片空白。靠删 manifest 来「解释」缺失，正是本规则要拦的行为。

## 推荐命令

```bash
# 全链路（结构 + 数学 + 证据 + 跨产物一致性）
python3 scripts/validate_report.py report.html \
  --manifest research_manifest.json \
  --evidence-dir research_sz002897/evidence \
  --out validation

# 只跑跨产物一致性（报告锚点 ↔ Claim Ledger ↔ manifest.evidence_refs）
python3 scripts/validate_report.py report.html \
  --manifest research_manifest.v3.json \
  --evidence-dir research_sz002897/evidence \
  --claim-only --out validation

# 只校验证据库（不读报告）
python3 scripts/validate_evidence.py research_sz002897/evidence --fail-on P0,P1,P2

# 摘录验证状态：重算并与落盘值比对（mismatch / critical unverified 即非 0）
python3 scripts/verify_excerpts.py research_sz002897/evidence
python3 scripts/verify_excerpts.py research_sz002897/evidence --write   # 只有确需刷新缓存时才写

# 报告锚点指纹：检查 / 盖章（不要手填）
python3 scripts/stamp_claim_fingerprints.py report.html \
  --evidence-dir research_sz002897/evidence --check
python3 scripts/stamp_claim_fingerprints.py report.html \
  --evidence-dir research_sz002897/evidence --write
```

返回 `PASS` 才能交付；返回 `FAIL` 时，生成器应根据 P0/P1 逐项修正，然后重新运行 Validator，直到通过。
**Validator 只输出 `PASS/FAIL + 错误码 + 定位 + 建议修复项`，绝不修改产物。**


## 不同估值方法的 Manifest 写法

- PE：`method=PE`，`linked_metric=net_profit_billion`。
- PS：`method=PS`，`linked_metric=revenue_billion`。
- PB：`method=PB`，`linked_metric=book_equity_billion`；Validator 校验倍数数学，但账面净资产需另有证据。
- DCF/DDM：`method=DCF`/`DDM`，`multiple=null`；Validator 不复算完整现金流模型，但仍校验总估值÷股本=目标价，并要求关键假设进入 evidence/manifest。
- SOTP：除 valuation 总结块外，同时填写 `sotp.parts` 做分部加总与利润口径对账。
